# 系统架构

## 1. 总体结构

```
微信小程序 / 浏览器演示台
        │  HTTPS + Bearer Token
        ▼
┌──────────────────────────────────────────────┐
│ Node.js 服务（零依赖）                        │
│  app.js        路由 / 错误处理 / 静态资源      │
│  lib/auth       HMAC Token                    │
│  lib/llm        DeepSeek 调用 + Mock 降级      │
│  lib/memory     长期记忆                       │
│  lib/conversation 消息 + 滚动摘要              │
│  lib/planner    方案 / 周课程 / 讲稿 / 音频    │
│  lib/billing    试用 / 计费 / 钱包             │
│  lib/referral   推荐链 / 佣金 / 结算           │
└───────┬───────────────┬──────────────┬────────┘
        │               │              │
   SQLite(WAL)      DeepSeek API     TTS（本机/云）
```

选择零依赖的原因：MVP 阶段最怕"装不上、跑不起来"。内置 `node:sqlite`、`fetch`、`node:test` 已经够用，部署只需要一个 Node 进程。

## 2. 一次完整请求的时序

### 2.1 对话 + 记忆 + 方案

```
POST /api/chat {text, wantPlan}
  ├─ 写入 messages(user)
  ├─ 读取 memories → buildMemoryText()
  ├─ LLM: memory-extract → {facts[]} → upsert memories（同 kind+key 覆盖）
  ├─ 若 wantPlan 或命中意图词：
  │     LLM: plan → 归一化 → 写 plans
  │     回一句"方案已排好"的引导语
  │  否则：
  │     LLM: chat（系统提示词 = 教练角色 + 对话规则 + 记忆块 + 最近 10 条）
  ├─ 写入 messages(assistant)
  ├─ 消息数 > 24 且未压缩 ≥ 16 条 → LLM: summary → users.summary
  └─ 返回 reply / plan / 本轮新增或更新的记忆
```

记忆是"边聊边记"而不是"聊完再总结"，这样用户中途退出也不丢关键信息。

### 2.2 生成课程音频

```
POST /api/plans/:id/weeks/:week/lessons
  └─ LLM: week-lessons → 3 节课（标题/目标/要点）→ 写 lessons(status=draft)

POST /api/lessons/:id/audio
  ├─ 若无 script：LLM: lesson-script（600~900 字纯口语讲稿）
  ├─ 写 lessons.script + 估算时长
  ├─ TTS: 清洗文本 → 合成 → 落盘 data/media/lesson-xxx.wav
  ├─ 解析 WAV 头取真实时长（准确计费需要）
  └─ 失败则 status=text_only，讲稿仍可用
```

音频按需生成（点开才合成），避免为没人听的课付 TTS 费用。

### 2.3 听课与计费

```
POST /api/sessions {lessonId}
  ├─ 体验额度 > 0 → 允许，funding=trial
  ├─ 额度为 0 且非会员 → 402 NEED_MEMBERSHIP
  ├─ 额度为 0 且会员但余额 < 10 秒的钱 → 402 NEED_TOPUP
  └─ 写 sessions(started_at, last_beat_at, status=active)

每 15 秒 POST /api/sessions/:id/heartbeat {playedSeconds}
  ├─ server_seconds = now - started_at（服务端时间，客户端改不了）
  ├─ reported_seconds = max(上次, 本次)
  └─ 返回预估费用、低余额提醒

暂停/离开 POST /api/sessions/:id/end {playedSeconds}
  ├─ billable = min(reported, server_seconds + 15, 4h)
  ├─ 体验优先：trialPart = min(billable, trialLeft)
  ├─ 剩余按 0.8 元/分钟计费，余额不足则只结算买得起的秒数
  ├─ 事务内：扣钱包 + 写 ledger + 关会话 + 分佣
  └─ 返回账单（体验秒数 / 计费秒数 / 扣费 / 余额 / 佣金笔数）
```

**为什么服务端时间优先**：客户端可以随意上报 `playedSeconds`，所以取"上报值"和"服务端时长 + 15 秒容差"的较小值，并设 4 小时上限。攻击者最多多听 15 秒，或反复开课——后者由"余额不足即停"和体验累计兜住。

**可以更强**：音频分片 + 签名 URL（每片 30 秒，服务端只对已请求的分片计时），或 HLS AES-128 加密 + 播放凭证。当前版本已把接口留好，替换 `startSession/heartbeat` 实现即可。

### 2.4 佣金

```
end() 事务内 → payCommissions({payerId, baseFen = 本次真实扣费})
  ├─ candidatesFor(payerId)
  │    ├─ 未达标（累计消费 < REFERRAL_QUALIFY_FEN）→ 不分佣，直接返回空
  │    ├─ cycle（默认）：找到直推人 → 用 payer 达标时分配好的 qualify_ordinal
  │    │                 → rate = ladder[(ordinal-1) % 3] → 第1个20%、第2个50%、第3个70%、第4个20%…
  │    ├─ depth：沿 referrer_id 上溯最多 50 层，rate = ladder[depth-1]
  │    └─ sequence：按序号递增，到 70% 后不回落
  ├─ 金额 = floor(base × rate / 10000)，受 capTotalBp（默认 100%）约束
  └─ 写 commissions(status=pending, depth, ordinal, rate_bp)
T+N 后 → settlePending() → 转入 wallets.commission_fen + ledger
提现 → wallets.frozen_fen + withdrawals(pending) → 运营打款
```

序号在「累计消费达标」的那一笔结算里分配（`billing.qualifyIfNeeded`），不是注册就占位。这样"注册小号占第 3 个"必须先真花 50 元，套利成本远高于收益。


## 3. 长期记忆设计

### 3.1 数据结构

| 字段 | 作用 |
| --- | --- |
| `kind` | 10 类：goal/level/subject/weakness/strength/preference/schedule/pace/motivation/constraint |
| `key` | 稳定标识（`exam`、`weak_topic`、`daily_time`），同一件事必须复用 |
| `value` | 一句可独立理解的中文 |
| `confidence` | 0.1–1，用户明说 0.9，推断最多 0.6；只增不减（`MAX`） |
| `hit_count` | 被提到几次，用于排序与"这条靠不靠谱" |

`UNIQUE(user_id, kind, key)` + `ON CONFLICT DO UPDATE` 保证"说第二遍是修正，不是新增"。每用户上限 80 条，超出按 `confidence DESC, updated_at DESC` 淘汰。

### 3.2 三层上下文

1. **长期记忆**：最多 24 条，按置信度与新鲜度排序，注入每类任务的系统提示词。
2. **滚动摘要**：消息超过 24 条后，每次把最老的 16 条压成 150 字提要，存在 `users.summary`，`summary_upto` 记录已覆盖条数。
3. **最近对话**：最近 10 条原文。

这样上下文长度是常数级，不会随对话轮数爆掉。

### 3.3 隐私

- 提示词明确禁止抽取手机号、身份证、住址等敏感信息。
- 用户可在「我的」页逐条删除记忆，或调 `DELETE /api/me/memories` 全部清空。
- 生产应补：导出、账号注销、删除后 30 天内物理清除。

## 4. 模型接入与降级

- 协议：OpenAI 兼容 `/chat/completions`，`response_format: json_object` 拿结构化输出。
- 五类任务各自独立提示词（`llm.js` 顶部常量），温度分别 0.2 / 0.5 / 0.6 / 0.7 / 0.8。
- JSON 容错：去 ```json 围栏 → 截取首个 `{` 到末个 `}` → 失败则重试一次并强调"只输出 JSON"。
- 没有 Key：走 `mock-llm.js` 规则引擎（正则抽画像、模板排方案、模板写讲稿），用于本地演示与自动化测试。
- 有 Key 但调用失败：降级 Mock 并打日志，接口不 500。生产建议改成"返回可读的失败提示 + 上报监控"，避免把规则内容当模型内容发给用户。

## 5. 语音合成

三种适配（`tts.js`）：

| provider | 用途 | 说明 |
| --- | --- | --- |
| `sapi` | 本机 Windows 语音 | 开发演示；受限环境会失败（`0x80045040`），失败即降级文本 |
| `http` | 云厂商 TTS | POST `{text, voice, format}` → `{audioBase64}` 或 `{audioUrl}`，按你的供应商改一行 |
| `mock` | 测试 | 只估算时长，不产出文件 |

讲稿朗读前会清洗：去 Markdown、去【】括号、去表情、合并空白。中文按 4.4 字/秒估算时长，WAV 则直接读头部字节率取真实时长。

## 6. 生产化改造清单

**必须**
- SQLite → PostgreSQL/MySQL（`schema.sql` 可平移；注意事务与并发计数用 `SELECT ... FOR UPDATE` 或原子 UPDATE）。
- 单进程 → 多实例：会话/限流状态外置到 Redis；音频走对象存储 + CDN，不要放本机磁盘。
- 异步化：讲稿与 TTS 用队列（BullMQ / 云 MQ），前端轮询或订阅进度；同步接口在 3 秒内返回。
- 微信支付：统一下单 → 支付回调（验签 + 幂等）→ `creditTopup`；退款走反向流水 + 佣金冲正。
- 日志与监控：结构化日志（含 traceId）、接口耗时、LLM 失败率、TTS 失败率、余额为负告警。
- 限流：按用户 + IP 限制 `/api/chat`（LLM 是最贵的资源），体验期用户更严。

**建议**
- 内容安全前置：讲稿入库前过文本审核，音频生成后过音频审核，命中即不下发。
- 提示词与模型版本化：`prompts/` 目录 + 版本号写进 plan，便于 A/B 与回溯。
- 评测集：50 条真实学生描述 + 人工评分（相关性/可执行性/无违规承诺），每次改提示词回归。

## 7. 容量估算

单节课 20 分钟、讲稿约 900 字：
- 方案生成：1 次调用，输入约 2k token，输出约 1.5k token。
- 每周课程：1 次调用，约 1.5k token。
- 每节讲稿：1 次调用，约 1.2k token。
- 音频：900 字 ≈ 4 分钟音频文件（16kHz 16bit 单声道 ≈ 7.7MB，转 MP3 后 ≈ 1MB）。

按 1000 名日活、人均 30 分钟听课估算：日音频合成约 1000 节、存储约 1GB/日（MP3），必须上对象存储 + 生命周期清理。
